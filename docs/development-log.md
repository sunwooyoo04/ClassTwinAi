## 1. AI 협업 원칙

### 1.1 3회 반복 규칙

동일한 오류가 3회 이상 반복될 경우 AI 의존을 중단하고 다음 방법으로 전환합니다:

1. 공식 문서·튜토리얼 직접 확인
2. 구글링 / Stack Overflow
3. 실제 런타임 로그 수집 후 AI에게 **로그를 같이** 질문

이 규칙은 AI가 잘못된 가설을 반복적으로 제시하는 상황을 막기 위한 안전장치입니다. 실제로 본 프로젝트에서 "자리배정 균형조건이 반영되지 않는다"는 증상을 AI에게만 물었을 때 여러 가설(가중치 부족, SA 수렴 부족, 페널티 상수 문제 등)이 제시됐지만, 실제 원인은 **프론트엔드가 빈 배열을 전송하던 구조적 버그**였습니다. 이 버그는 PowerShell 런타임 로그를 직접 수집해 AI에게 보여준 순간 단번에 드러났습니다.

### 1.2 "AI는 가설 생성기, 검증은 실제 환경"

AI가 내놓은 수정안을 그대로 적용하지 않고, 다음 4단계 루프로 처리합니다:

1. **가설 생성** (AI) — 원인과 수정안 제시
2. **코드 이해** (사용자) — AI의 설명을 읽고 납득
3. **실제 데이터 검증** (코드 실행) — pytest 회귀 테스트 + 실제 데이터로 확인
4. **수정 반영** — 검증 통과 시에만 커밋

이 루프 덕분에 AI가 만든 코드가 기존 기능을 의도치 않게 깨뜨리는 회귀 리스크가 구조적으로 최소화됩니다.

### 1.3 도구 역할 분리

| AI 도구 | 페르소나 | 주 역할 |
|---|---|---|
| **Claude** | 시니어 엔지니어 | 코드 읽기·수정, 알고리즘 튜닝, 디버깅 리드 |
| **Gemini** | 설명 전문가 | 복잡한 알고리즘 원리 설명, 프롬프트 최적화 |
| **Codex** | 보일러플레이트 생성기 | 간단한 함수 스켈레톤, 정규식 작성 |

Claude를 주력으로 선정한 이유는 **긴 컨텍스트 안에서 구조적 일관성을 유지**하는 능력이 가장 뛰어났기 때문입니다. 본 프로젝트는 `algorithm.py` 1,300줄, `main.py` 970줄, `api.js` 2,250줄 규모로, 한 번의 수정이 여러 파일에 영향을 줄 수 있어 전체 구조를 이해하고 수정하는 능력이 필수였습니다.

```
1. 사용자: 요구사항 서술 (버그 / 새 기능 / 개선 요청)

3. AI: 가설 제시 (원인과 수정 방향)
4. 사용자: 확인 / 반박 / 보충
```

이 플로우는 기본적으로 **PR 리뷰와 유사**합니다. AI가 코드를 작성하고 사용자가 리뷰어 역할을 합니다. 차이는 AI가 자기 코드를 스스로 검증한다는 점입니다.

## 3. 주요 의사결정 기록

### 3.1 시력·특수교육 페널티 설계 (옵션 1 vs 옵션 2)

**상황**: 교사가 "시력배려"를 5순위로 낮게 설정한 경우, 시력약함 학생을 뒷자리까지 허용할 것인가?

**옵션 1** (하드 플로어): 순위와 무관하게 시력약함 학생은 절대 5행에 가지 않도록 강제
**옵션 2** (완전 자유): 순위를 따라 가중치만 반영, 5순위면 거의 무시

**결정**: **옵션 2 채택**

**이유**: 옵션 1은 "시력배려 1순위"의 의미를 무의미하게 만듭니다. 어차피 강제라면 순위를 조절하는 UI 자체가 불필요해집니다. 사용자(교사)의 판단을 존중하되, 대신 "밀리더라도 3행까지" 로직으로 최소한의 보호를 제공하는 방향으로 갔습니다.

**코드 위치**: `backend/algorithm.py` `_score_seats()` 함수의 시력·특수교육 페널티 블록

---

### 3.2 1순위 가중치를 2.0 → 2.5로 변경한 이유

**상황**: 교사가 특수교육을 1순위, 시력배려를 2순위로 설정했는데, 시력배려 학생이 앞 2줄에 11명 다 들어가고 특수교육 학생(신동현, ADHD)이 3행으로 밀리는 현상 발생.

**분석**:
- 1순위 가중치 2.0, 2순위 1.5 → 차이 0.5
- 신동현 3행 페널티: `-50 × 2 × 2.0 = -200`
- 김현우(시력약함) 3행 페널티: `-50 × 2 × 1.5 = -150`
- 차이 50뿐 → SA가 다른 조건들(키, 성별)의 상쇄로 특수교육을 밀어냄

**결정**: **1순위 가중치 2.0 → 2.5로 변경**

**결과**:
- 1순위와 2순위 차이 0.5 → **1.0으로 확대**
- 신동현 3행 페널티: `-250`
- 김현우 3행 페널티: `-150`
- 차이 100 → SA가 "특수를 앞, 시력을 뒤로"를 확실히 선호

**코드 위치**: `backend/algorithm.py` `_init_balance_weights()` 함수, `w = {1: 2.5, 2: 1.5, ...}`

---

### 3.3 옆자리 요청은 좌우만 인정, 세로는 거절

**상황**: 추가고려사항 "유선우와 정민우 옆자리로"에서 "옆"을 어떻게 정의할 것인가?

**옵션**:
- (A) 상하좌우 인접 모두 인정 (4-방향)
- (B) 같은 행에서 좌우만 인정 (2-방향)

**결정**: **옵션 B 채택 (좌우만)**

**이유**: 한국어 "옆자리"는 일상적으로 좌우를 의미합니다. "앞뒤"는 "앞자리/뒷자리"로 별도 표현됩니다. 옵션 A로 구현하면 세로로 붙은 경우에도 "성공"으로 인식되어 교사의 기대와 어긋납니다.

**코드 위치**: `backend/algorithm.py` `_score_seats()` 함수의 `forced_adjacent` 블록

```python
if same_row and col_diff == 1:
    score += 250  # 같은 행 바로 옆
elif same_row and col_diff == 2:
    score += 50   # 같은 행 한 칸 건너 (차선책)
else:
    score -= 40 * col_diff + 60 * row_diff  # 세로로 떨어져 있으면 큰 페널티
```

### 3.4 추가고려사항의 힘을 +100 → +250으로 강화

**상황**: "유선우 정민우 옆자리로" + "시력배려 1순위" 동시 설정 시, 정민우(191cm 최장신)가 뒷줄에 남고 유선우만 앞자리로 가는 현상.

**분석**:
- 옆자리 보너스 +100 vs 시력배려 1순위 페널티 -60
- 정민우를 앞자리로 끌어올리려면 거기 있던 시력약함 학생이 뒤로 밀려야 함 → 그 학생의 시력 페널티 -60
- 옆자리 보너스 +100과 상쇄 후 순이익 +40 정도로 SA가 움직일 동기 약함

**결정**: **옆자리 보너스 +100 → +250으로 강화**

**결과**:
- +250은 시력약함 한 명 희생(-60)의 4배 이상
- SA가 "정민우를 앞자리로 + 시력약함 한 명을 3행으로"를 확실히 선택
- 사용자의 명시적 의도(textarea 입력)가 균형조건 우선순위를 이기도록 설계

**철학**: 추가고려사항은 "이번 한 번의 예외"이고 균형조건은 "일반 규칙"이다. 예외가 규칙을 이기는 것이 자연스럽다.

### 3.5 수동 조정 flags 재계산을 프론트가 아닌 백엔드에서

**상황**: seat3에서 두 자리를 swap하면 빨간 테두리(갈등주의) 표시가 사라지는 버그.

**원인**: 프론트가 swap 후 flags를 로컬에서 재계산하려 했는데, 이 로직이 `AppState.relations` 데이터를 필요로 했고, 이 데이터가 항상 로드되어 있지 않아 fallback 경로가 빈 값으로 처리됨.

**옵션**:
- (A) 프론트에서 `AppState.relations` 로드 보장
- (B) 백엔드 `/assignments/seat/evaluate` 엔드포인트가 swap 후 grid를 받아서 flags 재계산 후 돌려줌

**결정**: **옵션 B 채택**

**이유**:
- 프론트는 화면 렌더링만 담당하고, 모든 도메인 로직은 백엔드에 둔다는 원칙에 부합
- 프론트가 갖지 않은 관계 데이터를 백엔드는 항상 가지고 있음
- 향후 다른 수동 조정 기능이 추가되어도 같은 엔드포인트를 재사용 가능

**코드 위치**: `backend/main.py` `evaluate_seat_assignment()` 엔드포인트

## 4. 결정적 버그 발견 에피소드

### 4.1 "balance 빈 배열" 구조적 버그

**증상**: 자리배정 화면에서 균형조건을 아무리 드래그해도 결과가 바뀌지 않음. 알고리즘 튜닝을 아무리 해도 반영이 안 됨.

**가설 (AI 제시, 모두 틀림)**:
1. ❌ "가중치 차이가 작아서 효과가 미미함" → 가중치를 2배로 올려도 변화 없음
2. ❌ "SA iteration이 부족함" → 5000으로 올려도 변화 없음
3. ❌ "초기 배치가 로컬 최적에 갇힘" → 초기화 로직 바꿔도 변화 없음
4. ❌ "점수 함수 부호가 반대" → 부호 확인했지만 맞음

**전환점**: 3회 반복 규칙에 따라 AI 의존 중단. PowerShell에 진단 로그 추가 요청.

**진단 로그 추가**:
```python
print(f"⚖️ balance 수신: {conditions.balance}")
print(f"⚖️ 계산된 가중치: {assigner.balance_weights}")
```

**결과**:
```
⚖️ balance 수신: []
⚖️ 계산된 가중치: {'vision': 1.0, 'special': 1.0, ...}
```

**진짜 원인 발견**: 프론트엔드 `runSeatAssignment` 함수에서 **`balance: []`로 하드코딩** 되어 있음. 드래그 리스트를 DOM에서 읽어 payload에 포함시키는 로직이 애초에 없었음.

**수정**:
```javascript
// 추가된 코드
const balance = [];
document.querySelectorAll("#seat-plist .priority-item").forEach((item, idx) => {
  const label = item.querySelector(".priority-label")?.textContent?.trim() || "";
  if (label) balance.push({ label, priority: idx + 1 });
});
```

**교훈**: AI는 코드 내용에서 가설을 세우지만, 실제 런타임 데이터 흐름을 직접 볼 수는 없습니다. "입력이 올바르게 전달되고 있는가?"는 진단 로그 없이는 확인할 수 없는 층위의 문제입니다. 이 경험 이후 주요 엔드포인트에는 입력 로그를 먼저 찍는 것을 기본으로 삼았습니다.

### 4.2 좌석 누락 버그 (6×5 vs 5×6)

**증상**: 교실 크기를 5×6(30석)에서 6×5(30석)로 바꾸니 2명이 사라짐.

**조사**: 알고리즘은 두 경우 모두 30석을 할당했지만, 초기 배치 로직에서 "시력약함 학생을 앞 2줄에 우선 배치" 코드가 열(column) 수 기준으로 하드코딩된 루프였음. 5열 환경에서 6명을 넣으려다 1명이 `break`로 누락.

**수정**: 우선 학생이 앞 2줄에 다 들어가지 못하는 경우, 남은 학생을 **일반 큐의 앞에 prepend**하여 절대 누락되지 않도록 함.

**코드 위치**: `backend/algorithm.py` `assign()` 함수의 초기 배치 블록

---

### 4.3 학생 업로드 시 관계 데이터 누락

**증상**: 엑셀에 관계 데이터를 작성했는데 갈등 페어가 자리배정에 반영되지 않음.

**원인**: `/students/upload` 엔드포인트가 엑셀의 첫 시트(`학생목록`)만 읽고 있었음. 관계 데이터는 별도 업로드 API가 있었지만 프론트에서 호출되지 않음.

**수정**: 엔드포인트에서 `openpyxl`로 두 시트를 **한 번에** 읽고, 학생과 관계를 동시에 DB에 반영. `relations_added` 카운트를 응답에 포함해 사용자 가시성 확보.

**프론트 대응**: 업로드 직전에 `DELETE /relations`를 호출해 이전 관계 데이터가 누적되지 않도록 보장.

## 5. 프롬프트 전략

### 5.1 좋은 프롬프트의 조건

AI가 효율적으로 동작하도록 프롬프트에 포함시킨 요소들:

1. **현재 상태 명시**: "지금 코드는 X 상태이고, Y를 원한다"
2. **제약 조건**: "Z는 건드리지 마, W는 반드시 유지해"
3. **검증 기준**: "수정 후 pytest를 돌려서 4/4 통과해야 한다"
4. **작업 단위**: "한 번에 한 파일, 한 함수만 수정"

### 5.2 비효율 프롬프트 예시 (지양)

❌ "X를 수정해줘"
→ AI가 전체 컨텍스트를 추측해야 함, 불필요한 재작성 발생

❌ "이 코드 좀 봐줘"
→ 무엇을 봐야 하는지 모호, AI가 피상적 리뷰만 함

### 5.3 효율 프롬프트 예시 (지향)

✅ "현재 `_score_seats` 함수에서 시력 페널티는 행에 무관하게 -50이야. 이걸 행이 뒤로 갈수록 선형 증가하도록 `-50 × (r-1)`로 바꾸되, 앞 2줄(r < 2)은 0으로 유지해. 수정 후 test_seat_e2e.py가 4/4 통과해야 해. 실패하면 롤백."

→ 현재 상태 + 원하는 결과 + 제약 + 검증 기준이 모두 포함됨

## 6. 토큰 효율 전략

### 6.1 str_replace 핀포인트 편집

2,000줄이 넘는 `api.js`에서 `runSeatAssignment` 함수 하나를 수정할 때, 전체 파일을 재생성하지 않고 해당 함수만 `str_replace`로 교체합니다. 이로써:

- **토큰 소모**: 전체 재생성 대비 약 5% 수준
- **오류 리스크**: 다른 함수를 건드릴 가능성 0
- **리뷰 용이성**: diff가 명확해 리뷰가 쉬움

### 6.2 작업 단위 세분화

한 번에 "버그 고치고 기능 추가하고 리팩터링해줘"라고 요청하면 AI가 전체를 재작성하려 합니다. 대신:

1. 버그 수정 → 테스트 통과 확인
2. 기능 추가 → 테스트 통과 확인
3. 리팩터링 → 테스트 통과 확인

각 단계가 독립적이므로 중간에 실패해도 롤백 범위가 작습니다.

### 6.3 설명과 코드 생성 분리

Claude가 "이 알고리즘 원리 설명해줘"와 "이 함수 수정해줘"를 동시에 처리하면 둘 다 토큰을 많이 씁니다. 설명은 Gemini에게, 코드 수정은 Claude에게 분리해 요청했습니다.

## 7. 회귀 테스트 자동화

### 7.1 test_seat_e2e.py

자리배정 플로우 전체를 검증하는 4개 테스트:

1. **기본 배정 성공** — 30명 학생에 대해 자리배정이 정상 완료되는가
2. **갈등 페어 분리** — 갈등 관계가 있는 두 학생이 인접하지 않는가
3. **수동 swap 후 평가** — swap 후 통계와 flags가 올바르게 재계산되는가
4. **이력 기반 형평성** — 여러 번 배정 후 구석자리 누적이 균등한가

### 7.2 실행 시점

- AI가 코드를 수정한 **직후** (자동)

- git commit 전 (선택)
