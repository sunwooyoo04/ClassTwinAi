# ClassTwin AI — 기획 문서

> 이 문서는 ClassTwin AI 프로젝트의 기획 단계 의사결정과 요구사항 정의를 정리한 것입니다. 개발 과정에서 Claude(Anthropic)와 협업하여 작성되었으며, 프로젝트의 방향성과 설계 철학을 기록하는 용도입니다.

---

## 1. 프로젝트 배경

### 1.1 문제 인식

초·중·고등학교 담임교사는 매 학기 반배정·자리배정이라는 두 가지 대규모 의사결정을 수행해야 합니다. 이 작업은 다음과 같은 복합 변수를 동시에 만족시켜야 합니다:

- **학생 개별 속성**: 성별, 성적, 키, 시력, 주의력, 특수교육 대상 여부
- **학생 간 관계**: 갈등 페어, 친한 친구, 형제자매
- **배치 이력**: 과거 구석자리·앞자리 누적 경험
- **교사의 암묵 지식**: "이 학생은 저 학생 옆에 앉히면 안 된다"

30명 학급 기준 가능한 자리 조합은 30! = 약 2.65 × 10³² 가지이며, 교사가 머릿속에서 최적 해를 찾는 것은 수학적으로 불가능합니다. 현실에서는 수 시간의 수작업 끝에 "적당히 괜찮은" 해를 선택하게 되며, 이는 다음 세 가지 부작용을 낳습니다:

1. **시간 비용**: 한 번의 배정에 2~5시간
2. **주관성**: 교사마다 결과가 달라지며 객관적 근거 부재
3. **설명 불가능성**: 학부모가 "왜 우리 아이가 이 자리인가?"를 물었을 때 데이터 기반 답변 불가

### 1.2 솔루션 방향

본 프로젝트는 위 세 가지 부작용을 알고리즘으로 해결합니다:

| 부작용 | 해결 접근 |
|---|---|
| 시간 비용 | Simulated Annealing 기반 자동 최적화 (수 초 내 완료) |
| 주관성 | 점수 함수로 수치화된 의사결정, 가중치 조절 가능 |
| 설명 불가능성 | LLM이 각 학생의 배정 이유를 자연어로 자동 생성 |

## 2. 사용자 정의

### 2.1 주요 사용자 (Primary User)

**초·중·고 담임교사**, 특히 30~35명 규모의 일반 학급을 담당하며 연 2회(1학기/2학기) 자리배정, 연 1회 반배정을 수행해야 하는 교사.

### 2.2 사용자의 암묵 요구

인터뷰·관찰 대신 교사로부터 직접 들은 현장 요구를 바탕으로 다음을 도출했습니다:

- "시력 약한 애 뒷자리 가면 안 된다"
- "ADHD 있는 애는 교탁 근처로"
- "저 두 명은 절대 붙이면 안 된다"
- "키 큰 애 앞자리 가면 뒤에서 안 보인다"
- "지난번에 구석 갔던 애 이번엔 안쪽으로 돌려야 한다"
- "이 애는 이번 한 번만 앞자리로 해달라고 학부모가 부탁했다"

이 요구들은 형태가 다릅니다:

- **일반 규칙** (시력, 키 등) → 균형조건으로 모델링
- **절대 조건** (갈등 페어 분리) → 강한 페널티로 강제
- **일회성 예외** (이번 한 번만 앞자리로) → 추가고려사항으로 자연어 입력

이 세 층위를 UI에서도 명확히 분리했습니다: (1) 자동 도출 절대조건, (2) 드래그 우선순위 균형조건, (3) 자유 입력 추가고려사항.

## 3. 핵심 설계 결정

### 3.1 왜 Simulated Annealing인가

선택지를 검토했습니다:

| 방법 | 장점 | 단점 |
|---|---|---|
| 완전탐색 | 전역 최적 보장 | 30! 경우의 수로 불가능 |
| Greedy | 빠름 | 로컬 최적에 갇힘 |
| **Simulated Annealing** | **로컬 최적 탈출, 2000 iter 내 수렴** | 전역 최적 보장은 없음 |
| Genetic Algorithm | 병렬화 유리 | 튜닝 변수 많음, 복잡도 대비 이득 적음 |

SA를 선택한 이유는 **점수 함수 튜닝만으로 동작 방향을 제어**할 수 있기 때문입니다. 교사의 요구가 바뀌면 (예: "시력을 더 강하게 반영해줘") 가중치 한 줄만 수정하면 됩니다.

### 3.2 왜 드래그 우선순위인가

초기 설계에서는 각 균형조건에 체크박스와 1~10 슬라이더를 두려 했으나, 다음 이유로 **드래그 기반 순위 방식**으로 변경했습니다:

- **인지 부담 감소**: "얼마나 중요한가?"보다 "둘 중 뭐가 더 중요한가?"가 더 쉬움
- **직관적 시각화**: 위에서 아래로 나열된 순서가 곧 우선순위
- **모바일 친화**: 슬라이더보다 드래그가 터치 기기에서 정확

내부적으로 드래그 순위는 가중치 테이블로 변환됩니다:

```
1순위 = 2.5   (2순위와의 차이 1.0 — 최상위 명확한 우위)
2순위 = 1.5
3순위 = 1.0   (기본값)
4순위 = 0.7
5순위 = 0.5
```

1순위와 2순위의 차이를 의도적으로 크게(0.5 → 1.0) 벌린 것은 "1순위는 확실히 우선시돼야 한다"는 설계 철학 때문입니다.

### 3.3 왜 자연어 추가고려사항인가

드래그 우선순위만으로는 "이번 학기에 박지호를 앞자리로 해달라"처럼 **한 번만 적용되는 예외**를 표현할 수 없습니다. 이런 일회성 요구를 위해 별도 textarea를 두고 LLM으로 파싱합니다.

자연어 입력을 택한 이유:

1. **학습 곡선 제로**: 교사가 새 UI를 배울 필요 없음
2. **표현력 높음**: "유선우와 정민우 옆자리로" 같은 복합 조건도 가능
3. **Fallback 안전망**: LLM이 실패하면 규칙 기반 파서가 대체

LLM + Fallback **이중 구조**는 다음 규칙으로 설계되었습니다:

```
1. LLM (GPT-4o) 호출
2. LLM 응답이 유효한 JSON이면 → 사용
3. LLM 실패 / 빈 응답 / API 오류 → 규칙 기반 파서로 대체
4. 두 경우 모두 사용자에게는 "해석 결과"를 파란 notice로 보여줌
```

이로써 LLM 서버 장애나 키 미설정 상황에서도 기능이 중단되지 않습니다.

### 3.4 "밀리더라도 3행까지" 로직

시력배려·특수교육 학생이 많은 학급(예: 30명 중 11명 시력약함)에서는 앞 2줄(12석)에 모든 우선 학생을 넣을 수 없습니다. 이 경우 SA가 어디로 학생을 밀어낼지가 문제입니다.

초기 구현에서는 "앞 2줄 이하면 페널티 없음, 그 외 모두 동일 페널티"로 설계했으나, 이 경우 SA가 밀리는 학생을 4·5행에 배치하는 경우가 발생했습니다. 교사의 기대는 "밀리더라도 최대한 앞쪽(3행)에 두기"였습니다.

해결은 **행 위치에 따른 선형 페널티**였습니다:

```
시력배려 3행: -50 × 1 × bw["vision"] = -75  (2순위 기준)
시력배려 4행: -50 × 2 × bw["vision"] = -150
시력배려 5행: -50 × 3 × bw["vision"] = -225
```

뒤로 갈수록 페널티가 급격히 커지므로, SA는 자연스럽게 "밀리더라도 3행"을 선호하게 됩니다. 수학적 설계와 교사의 직관적 기대가 일치하도록 조정한 결정입니다.

## 4. 비기능 요구사항

### 4.1 성능
- 30명 학급 자리배정: 5초 이내
- 120명 학년 반배정: 15초 이내

### 4.2 가용성
- LLM 키 없이도 핵심 기능 동작 (규칙 기반 fallback)
- 서버 재시작 가능 (in-memory이지만 엑셀 재업로드로 즉시 복원)

### 4.3 설명 가능성
- 모든 배정 결과에 대해 "왜 이 자리인가" 질의 가능
- 점수 함수의 모든 페널티·보너스는 코드 주석과 README에 명시

### 4.4 안전성
- 교사가 우선순위를 낮게 설정해도 시력·특수교육 학생에 대한 최소한의 보호 유지 ("3행까지" 로직)
- 갈등 페어는 가중치와 무관하게 항상 분리 시도

## 5. 기술 스택 선정

| 레이어 | 기술 | 선정 이유 |
|---|---|---|
| 백엔드 | FastAPI (Python) | 자동 API 문서, 타입 힌트, 비동기 지원 |
| 알고리즘 | Python 순수 구현 | 외부 의존 최소화, 튜닝 용이성 |
| 프론트엔드 | Vanilla JS + HTML | 빌드 도구 없이 즉시 실행, 학습 곡선 제로 |
| LLM | OpenRouter (GPT-4o) | 단일 엔드포인트로 여러 모델 교체 가능 |
| DB | in-memory dict | 개발·시연용으로 충분, 영구 저장이 필요해지면 SQLite로 전환 가능 |

프레임워크 의존성을 최소화한 것은 "교사가 직접 로컬에서 돌릴 수 있어야 한다"는 배포 철학 때문입니다. Node.js, npm, 빌드 도구가 없어도 Python만 있으면 동작합니다.

## 6. 로드맵 (차기 개선)

현재 버전에서 완성된 기능 너머로, 다음 기능들이 차기 개선 후보입니다:

- **SQLite 영구 저장** — database.py 인터페이스만 교체하면 됨
- **배치 이력 추적 UI** — 학기별 자리 변화를 그래프로 시각화
- **학부모 열람 페이지** — 자녀 배정 이유만 필터링해 공유
- **스마트폰 반응형 UI** — 현재는 데스크톱 우선 설계
